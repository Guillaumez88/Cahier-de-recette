# Des comptes, des foyers, des partages : spécification

Écrit avant l'implémentation, pour être relu. Ce document fixe le modèle de données,
les règles, la migration de l'existant et l'ordre des travaux. Ce qui n'y figure pas
n'est pas prévu.

## Ce qui est demandé

1. **On ne peut rien modifier sans être connecté**, et plus rien n'est lisible sans
   compte : le lien public en lecture seule du 16 août est supprimé.
2. **Un foyer possède les données** : une bibliothèque, un livre de cuisine général,
   une liste de courses, un semainier, un placard.
3. **Plusieurs comptes dans un même foyer**, chacun avec un rôle : modification ou
   lecture.
4. **Partager un livre ou une recette** avec un compte d'un autre foyer, désigné par
   son adresse e-mail, en lecture seule, et seulement si ce compte existe.

## Le modèle

### Les objets

| Chemin | Ce qu'il porte | Qui le lit | Qui l'écrit |
|---|---|---|---|
| `utilisateurs/{uid}` | e-mail, foyer courant | son propriétaire | son propriétaire |
| `annuaire/{email}` | l'identifiant du compte qui porte cet e-mail | tout compte connecté qui connaît l'e-mail | son propriétaire, à l'inscription |
| `foyers/{foyerId}` | nom du foyer, date de création | ses membres | ses membres en modification |
| `foyers/{foyerId}/membres/{uid}` | e-mail, rôle | ses membres | ses membres en modification |
| `foyers/{foyerId}/recettes/{id}` | les recettes, comme aujourd'hui | ses membres, et les bénéficiaires d'un partage | membres en modification |
| `foyers/{foyerId}/livres/{id}` | la bibliothèque | idem | idem |
| `foyers/{foyerId}/articles/{id}` | la liste de courses | ses membres | membres en modification |
| `foyers/{foyerId}/creneaux/{id}` | le semainier | ses membres | membres en modification |
| `foyers/{foyerId}/placard/{id}` | le placard | ses membres | membres en modification |
| `foyers/{foyerId}/photos/{id}` | photos de plats | ses membres, bénéficiaires | membres en modification |
| `foyers/{foyerId}/illustrations/{id}` | photos d'étapes | idem | idem |
| `partages/{partageId}` | ce qui est partagé, par qui, avec qui | le propriétaire et le bénéficiaire | le propriétaire |

**Un seul foyer par compte pour commencer.** `utilisateurs/{uid}.foyer` désigne le
foyer courant. Le modèle en supporte plusieurs plus tard sans rien casser : c'est une
liste qui remplacera un champ.

### Les rôles

`modification` écrit tout dans son foyer. `lecture` ne fait que lire, exactement comme
le mode lecture seule actuel : c'est la même mécanique d'interface, la source du
verrou change seulement de nom.

Le rôle est porté par le document de membre, donc par le serveur. L'application le lit
une fois à la connexion, et le garde en mémoire de session.

### Le partage entre foyers

Un partage est un document, pas une copie :

```
partages/{id} = {
  foyer:         "<foyerId propriétaire>",
  type:          "livre" | "recette",
  reference:     "<id du livre ou de la recette>",
  recettes:      ["<id>", …],        // le contenu du livre au moment du partage
  beneficiaire:  "<uid>",
  emailBeneficiaire: "…",
  creeLe:        "…"
}
```

**Pourquoi la liste des recettes est écrite dans le partage.** Les règles Firestore ne
savent pas filtrer une requête de collection : un bénéficiaire ne peut pas demander
« les recettes du livre X du foyer Y », faute de pouvoir prouver à la règle que sa
requête se limite à ce livre. Il lit donc les recettes **une par une**, par leur
identifiant, et la règle vérifie que cet identifiant figure dans un partage dont il est
bénéficiaire. La liste est le manifeste de ce qui est accessible.

Conséquence assumée : un livre partagé ne se met pas à jour tout seul quand une recette
y est ajoutée. Le propriétaire repartage, ce qui réécrit le manifeste. C'est explicite,
et cela évite qu'un partage s'élargisse sans que personne l'ait décidé.

### Trouver un compte par son e-mail

`annuaire/{email}` porte l'identifiant du compte. L'e-mail est normalisé (minuscules,
espaces retirés) et sert d'identifiant de document : on ne peut donc lire que la fiche
d'une adresse qu'on connaît déjà, jamais parcourir l'annuaire. Partager avec une
adresse inconnue échoue franchement, avec le message « aucun compte à cette adresse ».

## Les règles, en résumé

```
function connecte()       { return request.auth != null; }
function membre(foyer)    { return exists(/…/foyers/$(foyer)/membres/$(request.auth.uid)); }
function peutEcrire(foyer){ return get(/…/foyers/$(foyer)/membres/$(request.auth.uid)).data.role == 'modification'; }
function partagee(foyer, id) { … un partage dont je suis bénéficiaire et qui contient id … }
```

- Lecture d'une donnée de foyer : `membre(foyer) || partagee(foyer, id)`.
- Écriture : `peutEcrire(foyer)`, plus les contrôles de forme actuels, conservés tels
  quels.
- `annuaire` : lecture par tout compte connecté, écriture réservée au compte qui s'y
  inscrit, et jamais de suppression.

**Le coût.** Chaque lecture d'un document partagé déclenche un `get()` de règle, qui
compte comme une lecture facturée. Les lectures d'un membre de foyer, elles, en
déclenchent une par requête, pas par document, tant que la règle se contente
d'`exists()` sur le document de membre. C'est la raison pour laquelle le rôle est lu
une fois et gardé en mémoire.

## La migration

L'existant est un foyer sans nom : 47 recettes, 47 photos, 124 illustrations, une liste
de courses, un semainier, un placard, une bibliothèque de trois livres.

1. Vous créez votre compte sur le site.
2. Un outil (`tools/migrer-vers-foyer.js`) crée `foyers/<id>`, vous y inscrit comme
   membre en modification, puis **copie** chaque document des sept collections
   globales vers `foyers/<id>/…`. Copie, pas déplacement : l'ancien reste en place.
3. Contrôle : l'outil relit et compte les documents des deux côtés, et refuse de
   déclarer la migration réussie tant que les comptes diffèrent.
4. Les anciennes collections sont supprimées **plus tard**, dans un second passage, une
   fois le nouveau modèle en service depuis quelques jours. Tant qu'elles existent,
   revenir en arrière ne coûte qu'un déploiement.

## Ce qui disparaît

- Le lien public en lecture seule, et la mention « Carnet en lecture seule ».
- Le code de la maison et la collection `appareils` : un appareil ne se déverrouille
  plus, c'est une personne qui se connecte. `menage/secret` peut être supprimé.
- L'inscription d'un appareil par les outils en ligne de commande : ils se connecteront
  avec un compte, par `--email` et `--mot-de-passe`.

## L'ordre des travaux

| Étape | Contenu | Livrable |
|---|---|---|
| 1 | Comptes : inscription, connexion, déconnexion, session persistante. `sync.js` sait ouvrir une session nominative au lieu d'une session anonyme. | On se connecte, rien d'autre ne change |
| 2 | Foyers : création à la première connexion, chemins de données sous `foyers/{id}`, migration de l'existant, règles. | Le carnet fonctionne, connecté, sur ses données migrées |
| 3 | Membres et rôles : inviter une adresse dans son foyer, choisir le rôle, retirer un membre. | Plusieurs personnes dans le foyer |
| 4 | Partages entre foyers : partager un livre ou une recette à une adresse, voir ce qu'on a reçu. | Le partage demandé |
| 5 | Nettoyage : suppression du code de la maison, de `appareils`, des anciennes collections. | Un seul mécanisme à comprendre |

Chaque étape est déployable seule et laisse le carnet utilisable. L'étape 2 est celle
qui demande une fenêtre : entre la migration et le déploiement, les écritures faites
sur l'ancien modèle seraient perdues.

## Ce que je signale, sans qu'on me le demande

- **Le foyer d'abord, les comptes ensuite.** Un compte sans foyer ne voit rien. La
  première connexion crée donc un foyer, sinon l'écran serait vide sans explication.
- **Un mot de passe oublié** se réinitialise par e-mail : l'API le fait, mais il faut
  l'écran qui va avec, et l'expéditeur par défaut de Firebase (`noreply@…`) atterrit
  souvent dans les indésirables.
- **Rien n'empêche la création de comptes** depuis le site : Firebase ne le permet pas
  sans fonction serveur payante. Un compte inconnu ne voit rien et ne peut rien, mais
  il consomme une ligne dans votre projet.
- **La liste de courses reste optimiste et hors ligne.** Cela ne change pas, mais le
  cache local devra être cloisonné par foyer, sinon changer de compte sur un même
  appareil afficherait la liste du précédent.
- **Le mode hors ligne dépend d'un jeton valide.** Aujourd'hui la session anonyme se
  renouvelle sans rien demander. Avec un compte, un jeton expiré hors ligne coupe
  l'accès jusqu'au retour du réseau.
